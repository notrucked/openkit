## Changes since the previous candidate

### In-place forward migration

Make a cold Data Root backup before updating. Stop the old App and keep its Data Root for the published v0.1.1 App. On startup, the Core database applies two additive migrations for Discord Reports, advancing the shipped Core migration journal from one entry to three. This update keeps existing data. Use the stopped-App procedure because the App-update helper admits only migration-free updates.

A Workspace operational backup restores only on the exact build that made it. Cold Data Root backups can be restored across releases. After a stopped-server restore, startup runs the required migrations. After migration, the previous image cannot run on the migrated Data Root. To roll back, restore the pre-update backup on the previous build.

### Verify Workers after the update

Once the new App is running and verified, acquire and activate the same-release Worker Runtimes image and match its active platform digest before the first Worker Turn. An incompatible image is refused before Worker effects with `worker_release_incompatible`. [Operator procedure](https://github.com/lingkaix/openkit/blob/v0.1.1-rc.1/skills/openkit-ops/references/nanocore-operations.en.md#verify-workers-after-an-app-update)

### Other changes

- NanoHost recovers an idle App replacement across the expected transport interruption. Before the first Worker Turn, verify authenticated readiness for the same NanoHost identity and deployment, a fenced predecessor and a higher connection generation. [#934](https://github.com/lingkaix/openkit/issues/934)
- Stable promotion gives the anonymous Worker Common lookup its own Docker configuration. The provenance verifier retains its registry authentication. [#937](https://github.com/lingkaix/openkit/issues/937)
- App update verification compares readiness with the previous boot. The candidate must accept product work and cannot add a readiness block or a newly failed subsystem. [#904](https://github.com/lingkaix/openkit/issues/904)
- After a reload fences NanoHost transport admission, the restart reason remains visible until a fresh App process starts. [#891](https://github.com/lingkaix/openkit/issues/891)
- DuckDB can initialize in the stock Worker Sandbox on cgroup v2 hosts. [#930](https://github.com/lingkaix/openkit/issues/930)
- Doctor reports installed Skill compatibility and App-update availability from published stable releases when the required access and release information are available. [#240](https://github.com/lingkaix/openkit/issues/240)
- App update status reports an absent receipt as absent. After a disconnect, use the known receipt ID to read status. [#905](https://github.com/lingkaix/openkit/issues/905)
- Safe reload checks the Gateway configuration against the Provider registry that will stay loaded. An incompatible combination is refused before publication. [#891](https://github.com/lingkaix/openkit/issues/891)

## Known issues

These disclosures apply to the v0.1.1 build.

### Current limitations and qualification

- Keep the original v0.1.0 Getting Started container. Its Data Root backups are stored in the container’s writable layer and removal deletes them. Use the one-time `--convert-getting-started` procedure to copy and verify existing backups and retain the stopped original. [Operator procedure](https://github.com/lingkaix/openkit/blob/v0.1.1-rc.1/skills/openkit-ops/references/nanocore-operations.en.md#getting-started-bridge-settings) [#902](https://github.com/lingkaix/openkit/issues/902)
- DeepSeek Worker execution remains disabled (#868). Choose another Worker Agent.
- The acceptance window for the reviewed class C findings in the Debian bookworm base ends at 00:05 UTC on 2026-12-17. Debian trixie evaluation and VEX for unreachable components are 0.1.x follow-ups. The persistence-smoke correction now checks the SQLite-owned Workspace record. [#850](https://github.com/lingkaix/openkit/issues/850) · [#856](https://github.com/lingkaix/openkit/issues/856) · [#866](https://github.com/lingkaix/openkit/issues/866)
- Full verified staging and quarantine remain incomplete (#776). Existing conversation Threads can still admit Knowledge maintenance role Turns (#857).
- Hosted reported-activity latency remains under review (#848). Hosted test-container Docker-socket exposure (#846) and an unjoined image-refusal fixture writer (#847) remain tracked.
- Older recovery refusals can cancel unrelated native barriers (#863); historical no-citation Knowledge Manager Chat receipt replay can change its explanation (#864); attachment-only Composer input can be refused by Chat message publication (#865).
- Candidate CI and a fresh persistent Worker Turn on both architectures are required for this release. Deployment and credential qualification are separate checks on the published release.

These issues are tracked in #177. Release admission also requires the current release-blocker reconciliation; disclosure alone is not a waiver.

### Host and deployment

- A combined Provider and Gateway change can still require an App restart. The same applies when restoring a configuration that uses startup-owned fields. Verify the effective configuration after restart. [#891](https://github.com/lingkaix/openkit/issues/891)
- The v0.1.0 release record contains the first exact-product Worker readiness verdict. For later NanoHost runtime-target changes, the release record states the new verdict. [#120](https://github.com/lingkaix/openkit/issues/120)
- Worker runtime-file credential delivery is unavailable on stock boot and fails closed. Use gateway-only grants for MCP credentials. [#926](https://github.com/lingkaix/openkit/issues/926)
- A runtime-file delivery refusal can leave a non-secret preparation plan, environment snapshot and empty mountpoint. [#927](https://github.com/lingkaix/openkit/issues/927)
- Runtime-file credentials for persistent Worker images (#480) and the managed User-scoped credential lifecycle (#578) remain open until live qualification passes (#604).
- Package downloads can be refused when processes sharing one socket have different policy identities (#135).
- A package download can fail before an HTTP event without diagnostics that connect the failure to the affected request (#136).
- Idle backend bindings are not automatically evicted to make room for other work (#157).
- Workspace backup, restore and move cover one Workspace at a time. A Core Data Root backup omits NanoHost execution volumes. Preserve the volumes separately when recovery needs them. [#158](https://github.com/lingkaix/openkit/issues/158)
- This release supports one execution backend and cannot place work across mixed backends (#171).
- Execution quotas are not yet implemented (#172).
- Queued work uses first-in-first-out admission; fairness and aging policies are deferred (#173).
- Dynamic fleet selection and placement affinity are not yet supported (#175).
- Multi-process NanoCore scheduling, high availability and hot failover are not supported (#176).
- NanoCore does not yet emit every Turn-chain span that the telemetry specification targets (#219).
- Server operations shows cleanup work from its supported sources. The view is bounded and can report missing, stale or unavailable observations. [#226](https://github.com/lingkaix/openkit/issues/226)

- Remote MCP does not yet provide browser OAuth login; use the supported static bearer route (#145).
- External Agent clients use the user's authorization rather than independent Agent identities (#152).
